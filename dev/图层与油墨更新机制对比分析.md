# 图层切换 vs 油墨切换：更新机制对比分析

## 一、问题描述

**现象对比：**

- **图层切换**：点击checkbox → 画面立即轻松更新 ✅
- **油墨切换**：点击眼睛图标 → 整个页面重载，体验差 ❌

**用户诉求：**
能否让油墨清单参考图层的更新方式，实现即时渲染，避免整页重载？

---

## 二、图层更新机制深度剖析

### 2.1 核心架构

**数据流：**

```
用户点击checkbox
  ↓
optionalContentConfig.setVisibility(groupId, visible)  // 更新配置对象
  ↓
触发 "optionalcontentconfig" 事件
  ↓
pdfViewer.optionalContentConfigPromise = newPromise  // 更新promise
  ↓
pdfViewer.refresh(false, { optionalContentConfigPromise })  // 刷新渲染
  ↓
pageView.update({ optionalContentConfigPromise })  // 更新每个页面
  ↓
页面重新渲染（使用新的optionalContentConfig）
  ↓
Worker在生成operatorList时跳过不可见的图层内容
```

### 2.2 关键代码分析

**1. 图层点击事件处理** (`web/pdf_layer_viewer.js:72-85`)

```javascript
const setVisibility = () => {
  const visible = input.checked;
  // 直接更新配置对象（配置对象是共享的，不是静态类）
  this._optionalContentConfig.setVisibility(groupId, visible);

  const cached = this._optionalContentVisibility.get(groupId);
  if (cached) {
    cached.visible = visible;
  }

  // 触发事件，传递更新后的配置
  this.eventBus.dispatch("optionalcontentconfig", {
    source: this,
    promise: Promise.resolve(this._optionalContentConfig), // ← 关键：传递配置对象
  });
};
```

**2. App监听并更新Promise** (`web/app.js:2465-2468`)

```javascript
eventBus._on(
  "optionalcontentconfig",
  evt => (pdfViewer.optionalContentConfigPromise = evt.promise), // ← 更新promise
  opts
);
```

**3. PDFViewer更新Promise并触发刷新** (`web/pdf_viewer.js:2038-2058`)

```javascript
set optionalContentConfigPromise(promise) {
  if (!(promise instanceof Promise)) {
    throw new Error(`Invalid optionalContentConfigPromise: ${promise}`);
  }

  if (!this._optionalContentConfigPromise) {
    return;
  }

  this._optionalContentConfigPromise = promise;
  // 关键：调用refresh，传递新的配置promise
  this.refresh(false, { optionalContentConfigPromise: promise });

  this.eventBus.dispatch("optionalcontentconfigchanged", {
    source: this,
    promise,
  });
}
```

**4. 页面更新** (`web/pdf_page_view.js:676-700`)

```javascript
update({
  scale = 0,
  rotation = null,
  optionalContentConfigPromise = null,  // ← 接收新的配置promise
  drawingDelay = -1,
}) {
  this.scale = scale || this.scale;
  if (typeof rotation === "number") {
    this.rotation = rotation;
  }
  if (optionalContentConfigPromise instanceof Promise) {
    // 更新页面的配置promise
    this._optionalContentConfigPromise = optionalContentConfigPromise;
    // 后续渲染会使用这个新的promise
  }
  // ... 触发重新渲染
}
```

**5. Worker在渲染时使用配置** (`src/core/evaluator.js`)

Worker在生成operatorList时，会：

- 解析PDF内容中的 markedContent（标记内容，用于图层）
- 检查 optionalContentConfig 中的可见性
- 如果图层不可见，跳过该内容，不生成对应的操作符

### 2.3 关键特性

**✅ 配置对象是可传递的：**

- `OptionalContentConfig` 是一个普通对象实例
- 通过事件和Promise传递给渲染流程
- Worker在渲染时使用传递的配置

**✅ 无需重新加载文档：**

- 只是更新配置对象的可见性属性
- 页面重新渲染时使用新配置
- Worker根据新配置生成operatorList

**✅ 即时响应：**

- `setVisibility()` 只是更新对象属性
- `refresh()` 触发重新渲染
- 无明显延迟和闪烁

## 三、油墨更新机制深度剖析

### 3.1 当前架构（方案A）

**数据流：**

```
用户点击眼睛图标
  ↓
ColorConverter.updateColorState(colorName, visible)  // 更新主线程静态配置
  ↓
触发 "inkstatechanged" 事件
  ↓
app.js: 保存视图状态
  ↓
app.open({ url })  // 重新加载整个文档 ❌
  ↓
创建新的Worker线程
  ↓
pdfDocument.updateColorFilterConfig(config)  // 同步配置到Worker
  ↓
清除缓存并重新渲染
  ↓
恢复视图状态
```

### 3.2 关键代码分析

**1. 油墨点击事件处理** (`web/pdf_ink_list_viewer.js:564-593`)

```javascript
inkItem.addEventListener("click", () => {
  // 单个通道或专色点击事件
  ink.visible = !ink.visible;

  // 保存状态到当前页面的持久化存储
  this._setInkVisibility(this.currentPageNumber, ink.name, ink.visible);

  // 更新ColorConverter（主线程的静态配置）
  const channelNameMap = {
    青色: "Cyan",
    洋红色: "Magenta",
    黄色: "Yellow",
    黑色: "Black",
  };
  const colorConverterName = channelNameMap[ink.name] || ink.name;
  ColorConverter.updateColorState(colorConverterName, ink.visible); // ← 只更新主线程

  // 触发 inkstatechanged 事件
  this.eventBus.dispatch("inkstatechanged", {
    source: this,
    inks: this.inks,
  });
});
```

**2. App监听并重新加载文档** (`web/app.js:2317-2448`)

```javascript
eventBus._on("inkstatechanged", async evt => {
  // 保存当前页码和缩放
  const currentPage = this.page;
  const currentScale = this.pdfViewer.currentScale;

  // ❌ 重新打开文档（完全重新加载）
  await this.open({ url: this.url });

  // 同步配置到Worker线程
  await this.pdfDocument.updateColorFilterConfig(config);

  // 清除缓存并重新渲染
  for (const { view: pageView } of visiblePages.views) {
    pageView.pdfPage.clearOperatorListCache();
    pageView.reset();
  }
  this.forceRendering();

  // 恢复视图状态
  this.page = currentPage;
  this.pdfViewer.currentScale = currentScale;
});
```

**3. Worker通信机制** (`src/core/worker.js`)

```javascript
handler.on("UpdateColorFilterConfig", async function (data) {
  const { ColorConverter } = await import("./color_converter.js");
  ColorConverter.setColorFilterConfig(data.config); // 更新Worker线程的静态配置
  return true;
});
```

### 3.3 核心问题

**❌ ColorConverter是静态类，无法传递：**

- 主线程和Worker线程各有独立的ColorConverter静态实例
- 更新主线程配置不会影响Worker线程
- 必须通过消息机制同步配置

**❌ 颜色过滤在转换阶段，不在operatorList生成阶段：**

- 图层过滤：在operatorList生成时跳过不可见内容
- 颜色过滤：在颜色转换时修改颜色值
- 颜色转换发生在每次渲染时，需要重新执行

**❌ 配置同步需要重新加载：**

- Worker已经创建，静态配置已初始化
- 无法动态更新Worker的静态配置
- 只能重新创建Worker（即重新加载文档）

## 四、核心差异对比

| 对比维度       | 图层机制                          | 油墨机制（当前方案A）    |
| -------------- | --------------------------------- | ------------------------ |
| **配置存储**   | 对象实例（OptionalContentConfig） | 静态类（ColorConverter） |
| **配置传递**   | ✅ 通过Promise传递                | ❌ 无法传递，需消息同步  |
| **过滤时机**   | ✅ operatorList生成时             | ❌ 颜色转换时            |
| **Worker通信** | ✅ 不需要                         | ❌ 必须通过消息同步      |
| **文档重载**   | ✅ 不需要                         | ❌ 必须重新加载          |
| **更新方式**   | ✅ refresh + pageView.update      | ❌ open + 缓存清除       |
| **用户体验**   | ✅ 即时响应，无闪烁               | ❌ 明显延迟和闪烁        |
| **性能开销**   | ✅ 低（只重新渲染）               | ❌ 高（重新解析文档）    |
| **实现复杂度** | ✅ 简单                           | ❌ 复杂（需Worker通信）  |

## 五、参考图层机制改造油墨的可行性分析

### 5.1 方案D：参考图层机制的油墨过滤（理想方案）

#### 核心思路

将 ColorConverter 从静态类改造为可传递的配置对象，类似 OptionalContentConfig。

#### 需要的架构变更

**1. 创建ColorFilterConfig类**

```javascript
// 新文件：src/display/color_filter_config.js

class ColorFilterConfig {
  #colors = new Map([
    ["Cyan", true],
    ["Magenta", true],
    ["Yellow", true],
    ["Black", true],
  ]);

  constructor(initialConfig = {}) {
    if (initialConfig.colors) {
      this.#colors = new Map(Object.entries(initialConfig.colors));
    }
  }

  setVisibility(colorName, visible) {
    this.#colors.set(colorName, visible);
  }

  isVisible(colorName) {
    return this.#colors.get(colorName) !== false;
  }

  getConfig() {
    return {
      colors: Object.fromEntries(this.#colors),
    };
  }

  filterCMYK(cmyk) {
    return [
      this.isVisible("Cyan") ? cmyk[0] : 0,
      this.isVisible("Magenta") ? cmyk[1] : 0,
      this.isVisible("Yellow") ? cmyk[2] : 0,
      this.isVisible("Black") ? cmyk[3] : 0,
    ];
  }

  filterSpot(spotName, spotValue) {
    return this.isVisible(spotName) ? spotValue : 0;
  }
}
```

### 5.2 方案E：混合方案（轻量级改进）

#### 核心思路

保持当前架构，但优化重新加载流程，减少用户感知到的延迟。

#### 优化措施

**1. 智能缓存保持**

```javascript
// 只清除受影响的缓存
for (const { view: pageView } of visiblePages.views) {
  // 不清除commonObjs（字体、图像等共享资源）
  // 只清除operatorList
  if (pageView.pdfPage?.clearOperatorListCache) {
    pageView.pdfPage.clearOperatorListCache();
  }
}
```

**2. 预加载优化**

```javascript
// 在用户点击前预先同步配置
eventBus._on("inkstatechanging", async evt => {
  // 提前同步配置到Worker
  await this.pdfDocument.updateColorFilterConfig(evt.config);
});
```

**3. 渐进式渲染**

```javascript
// 不等待所有页面完成，逐页渲染
await this.open({ url: this.url });
await this.pdfDocument.updateColorFilterConfig(config);

// 立即渲染可见页面
this.forceRendering();

// 不等待渲染完成就恢复状态
this.page = currentPage;
this.pdfViewer.currentScale = currentScale;
```

**4. 视觉过渡优化**

```javascript
// 添加淡入淡出效果
pdfViewer.container.style.opacity = 0.5;
await this.open({ url: this.url });
pdfViewer.container.style.transition = "opacity 0.2s";
pdfViewer.container.style.opacity = 1;
```

#### 改动范围

**需要修改的文件：**

- `web/app.js` - 优化重新加载流程（~50行）

**优点：**

- ⭐ 实现简单，改动最小
- ⭐ 保持现有架构稳定性
- ⭐ 可以逐步优化

**缺点：**

- ❌ 仍然需要重新加载文档
- ❌ 用户体验改善有限

### 5.3 方案F：不重载的增量更新（折中方案）

#### 核心思路

不重新加载文档，但使用更智能的方式同步Worker配置并触发重新渲染。

#### 关键实现

**1. Worker配置即时同步**

```javascript
// web/app.js
eventBus._on("inkstatechanged", async evt => {
  // 获取当前配置
  const config = ColorConverter.getColorFilterConfig();

  // 立即同步到Worker（不重新加载文档）
  await this.pdfDocument.updateColorFilterConfig(config);

  // 清除缓存
  const visiblePages = this.pdfViewer._getVisiblePages();
  for (const { view: pageView } of visiblePages.views) {
    // 清除operatorList缓存
    if (pageView.pdfPage?.clearOperatorListCache) {
      pageView.pdfPage.clearOperatorListCache();
    }
    // 清除渲染缓存
    if (pageView.pdfPage?.objs) {
      pageView.pdfPage.objs.clear();
    }
  }

  // 使用refresh而不是open
  this.pdfViewer.refresh(false, {});

  // 或者直接触发重新渲染
  this.forceRendering();
});
```

**2. 确保Worker配置实时生效**

关键问题：Worker的ColorConverter是静态类，如何确保新配置生效？

**可能的解决方案：**

- Worker消息处理器立即更新静态配置
- 渲染前确保配置已同步
- 使用await确保同步完成

#### 可行性分析

**✅ 技术可行性：**

- Worker通信机制已存在（updateColorFilterConfig）
- 缓存清除机制已存在（clearOperatorListCache）
- 渲染触发机制已存在（forceRendering）

**❓ 潜在风险：**

- Worker的静态配置更新后，是否立即影响后续渲染？
- 缓存清除是否彻底？
- 是否存在竞态条件？

**测试方案：**

1. 更新配置
2. 同步到Worker（await）
3. 清除缓存
4. 触发渲染
5. 验证颜色过滤是否生效

#### 改动范围

**需要修改的文件：**

- `web/app.js` - 修改事件处理逻辑（~30行）

**优点：**

- ⭐⭐⭐ 实现相对简单
- ⭐⭐⭐⭐ 用户体验大幅改善
- ⭐⭐⭐⭐ 性能显著提升

**缺点：**

- ❓ 需要验证可靠性
- ❓ 可能存在配置同步时机问题

## 八、核心技术差异总结

### 8.1 为什么图层可以即时更新？

**原因1：配置对象可传递**

- OptionalContentConfig是普通对象
- 通过Promise在主线程和Worker间传递
- Worker使用传递的配置，不依赖本地状态

**原因2：过滤在operatorList生成阶段**

- Worker生成operatorList时检查图层可见性
- 不可见的内容直接跳过，不生成操作符
- 后续渲染时自然不会显示

**原因3：状态更新机制成熟**

- PDFViewer.refresh() 方法设计完善
- pageView.update() 支持配置更新
- 整个流程无需重新加载文档

### 8.2 为什么油墨需要重新加载？

**原因1：静态类无法传递**

- ColorConverter是静态类
- 静态属性在模块加载时初始化
- 主线程和Worker各有独立实例

**原因2：过滤在颜色转换阶段**

- 颜色转换发生在每次渲染时
- 需要Worker的ColorConverter使用新配置
- 静态配置更新后需要确保生效

**原因3：配置同步机制的局限**

- 消息同步后，静态配置已更新
- 但已缓存的operatorList可能仍使用旧颜色
- 必须清除缓存并重新生成

### 8.3 根本差异

| 维度         | 图层（OptionalContentConfig）  | 油墨（ColorConverter）     |
| ------------ | ------------------------------ | -------------------------- |
| **数据结构** | 对象实例                       | 静态类                     |
| **传递方式** | Promise传递                    | 消息同步                   |
| **作用阶段** | operatorList生成时（内容过滤） | 颜色转换时（颜色修改）     |
| **影响范围** | 跳过内容（不生成操作符）       | 修改颜色值（操作符已生成） |
| **缓存策略** | 缓存operatorList可复用         | 缓存operatorList不可用     |

```javascript
eventBus._on("inkstatechanged", async evt => {
  console.log("[app.js] 收到inkstatechanged事件（方案F：增量更新）");

  // 获取当前配置
  const config = ColorConverter.getColorFilterConfig();

  try {
    // 步骤1：同步配置到Worker（不重新加载文档）
    if (this.pdfDocument?.updateColorFilterConfig) {
      await this.pdfDocument.updateColorFilterConfig(config);
      console.log("[app.js] 配置已同步到Worker线程");
    }

    // 步骤2：清除受影响页面的缓存
    const visiblePages = this.pdfViewer._getVisiblePages();
    for (const { view: pageView } of visiblePages.views) {
      if (pageView.pdfPage) {
        // 清除operatorList缓存
        if (pageView.pdfPage.clearOperatorListCache) {
          pageView.pdfPage.clearOperatorListCache();
        }
        // 清除对象缓存
        if (pageView.pdfPage.objs) {
          pageView.pdfPage.objs.clear();
        }
      }
      // 重置页面视图
      pageView.reset();
    }

    // 步骤3：触发重新渲染（不重新加载文档）
    this.forceRendering();

    console.log("[app.js] 增量更新完成");
  } catch (error) {
    console.error("[app.js] 增量更新失败，回退到完全重载:", error);
    // 回退到方案A
    await this.open({ url: this.url });
  }
});
```
